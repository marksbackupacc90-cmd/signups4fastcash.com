# S4FC Network — AI Development Guidelines

This file is the durable project-context anchor for future AI-assisted work.
Keep it aligned with the running code. When code and this document differ, the
code is authoritative; update this document when behavior or architecture
changes.

## Platform identity

- **Product:** Signups4FastCash.com, also referred to as **S4FC Network**.
- **Product direction:** A premium, dark-mode rewards, offer-discovery, and
  earning platform. The dashboard interaction model takes inspiration from
  EarnX.gg; retain S4FC's own name, content, and visual identity.
- **Visual system:** Dark charcoal/slate surfaces, accessible sans-serif text,
  cyan/neon accents, responsive layouts, and reusable dashboard cards. Shared
  tokens and global styling are in [`src/index.css`](./src/index.css).
- **AI wording:** The product brief describes a GPT-style platform, but the
  active generative-AI integration uses Google's Gemini SDK and
  `GEMINI_API_KEY`; do not describe it as using OpenAI/GPT unless that changes.
- **Truth in presentation:** Dashboard preview and presentation-seed values are
  mock data. Never present them as real users, conversions, balances, or paid
  withdrawals.

## Active technology and runtime environments

### Application stack

- **Runtime:** Node.js 20+.
- **Frontend:** React 19, TypeScript, Vite, Tailwind CSS v4, custom CSS theme
  tokens, `lucide-react` icons, and Motion animations.
- **Backend:** Express 4 in TypeScript (`server.ts`), run by `tsx` in
  development and bundled with `esbuild` for production.
- **Realtime:** The `ws` package provides `/ws/activity` and authenticated,
  same-origin `/ws/notifications` WebSocket endpoints.
- **Database:** PostgreSQL via `pg`. Schema creation and versioned migrations
  are implemented in `server.ts`; there is no ORM.
- **Authentication/security integrations:** Google OAuth, `bcryptjs` password
  hashing, HTTP-only session cookies, Helmet, and configured CORS.
- **External integrations:** CPX Research, configured affiliate/offer feeds,
  Resend email, and Google Gemini. These integrations require their respective
  environment variables and provider configuration; do not assume they are
  enabled in every environment.

## PostgreSQL models

The tables below are declared by the current server schema initializer and its
migrations. Some tables are created only after PostgreSQL is configured. This
is a table/model inventory, not an ORM model layer.

### Accounts and security

- `users`: account identity, profile, wallet fields, and referral attribution.
- `auth_sessions`, `account_devices`, `fraud_flags`, `notifications`:
  persistent sessions, device/fraud signals, and user notices.
- `admin_access`, `admin_audit_log`: administrative access and audit records.

### Wallets and games

- `transactions`, `survey_reward_balances`, `cpx_transactions`:
  dollar-wallet ledger, separate points wallet, and CPX callback state.
- `withdrawal_requests`, `survey_payout_requests`: cash-out requests and
  point-payout requests.
- `game_rps_games`: single-player RPS history.
- `rps_lobbies`, `rps_lobby_moves`, `rps_matches`, `rps_house_ledger`: PvP
  rooms, private moves, match results, and recorded rake.

### Referrals

- `referral_code_aliases`, `referrals`, `referrals_ledger`,
  `referral_offer_clicks`: referral-code lookup, attribution/status,
  commissions, and attributed offer clicks.

### Offers and attribution

- `offers`, `offer_campaigns`, `offer_milestone_tiers`,
  `offer_milestone_events`, `user_offer_milestone_progress`,
  `user_offer_milestone_claims`: offer configuration and trusted milestone
  progress/claim state.
- `click_logs`, `live_offer_credits`, `user_offer_entries`,
  `user_offer_completion_reports`, `offer_issue_reports`: click attribution,
  credited feed events, and user offer/support reports.
- `offer_impressions`, `offer_analytics_events`, `offer_revenue_events`,
  `offer_security_events`, `offer_feed_sync_runs`: offer analytics, verified
  revenue/security events, and feed-sync history.

### Support and community

- `support_tickets`, `support_chat_messages`, `community_chat_messages`,
  `direct_messages`, `friend_connections`, `site_messages`: user/admin support,
  chat, direct messages, friend links, and site messages.

### Analytics, communications, and operations

- `schema_migrations`, `background_worker_runs`,
  `weekly_leaderboard_entries`, `analytics_counters`,
  `ledger_integrity_runs`, `analytics_report_checkpoints`, `visitor_events`,
  `newsletter_subscribers`: migration state, scheduled work, leaderboard,
  analytics, visitor events, and email subscription state.

`community_chat_messages` is cleared during current server initialization;
do not treat that table as durable chat history without changing the startup
behavior deliberately.

## Architecture and existing platform behavior

### Users and authentication

- `users` is the primary account relation. It supports Google identity and
  email/username plus password accounts. Passwords are bcrypt hashes; plaintext
  passwords must never be persisted or logged.
- Sessions are stored in `auth_sessions` and issued in an HTTP-only,
  `SameSite=Lax` cookie, marked `Secure` in production.
- Core routes: `GET /api/auth/me`, `POST /api/auth/signup`,
  `POST /api/auth/login`, Google OAuth at `/api/auth/google` and callback
  `/api/auth/google/callback`, `POST /api/auth/logout`, and profile routes.
- Authenticated APIs must continue to use the existing authentication
  middleware. Admin and owner-admin routes have separate authorization checks;
  never treat possession of an account session as admin authorization.

### Wallets, rewards, and cash-outs

**Do not conflate the two wallet systems.**

1. **Dollar-denominated wallet:** `users.balance`, with changes recorded in
   `transactions`. Verified affiliate postbacks and configured referral
   commissions use this wallet.
2. **Survey-points wallet:** `survey_reward_balances.points`; **100 points =
   $1.00**. CPX surveys, native RPS, milestone rewards, and point-denominated
   PvP use this wallet. Cash-out requests are separate records and must reserve
   balances transactionally.

Reward mutations must be server-authoritative, use integer cents/points as
appropriate, and be protected against insufficient funds, duplicate events,
concurrent updates, and retries. Do not mark a withdrawal as paid merely
because it was requested; payment/manual completion is a separate workflow.

### Offers, callback verification, and tracking

- Public offers and campaign administration are served by `/api/offers` and
  `/api/admin/offers` routes. Offer clicks use `/go/:id` and `click_logs` to
  preserve click/user/offer attribution for server-to-server callbacks.
- **Affiliate callback:** `GET` or `POST /api/v1/callbacks/postback`.
  `POSTBACK_SECRET` authenticates the canonical
  `<click_id>.<user_id>.<offer_id>.<milestone_step>.<payout_cents>` payload.
  The handler checks the click/Sub-ID sequence, account eligibility, active
  configured tier and exact payout; it then atomically writes an idempotent
  `OFFER_COMPLETION` transaction and credits `users.balance`.
- **CPX callback:** `GET /api/cpx/postback`. `CPX_SECURE_HASH` verifies the
  provider signature; status `1` credits points and status `2` reverses a
  prior credit. Callback state is tracked in `cpx_transactions`. Use the
  provider's documented signature format; do not replace it casually.
- **Milestone callback:** `POST /api/offers/milestones`. It requires
  `MILESTONE_CALLBACK_SECRET`, a recent timestamp (five-minute acceptance
  window), unique provider event ID, and a valid HMAC. Progress is monotonic,
  duplicate events/claims are idempotent, and crossed tiers are credited
  server-side in the points wallet. Client-reported level changes are not
  trusted.
- **Feed synchronization:** external offer feeds are optional/configured,
  normalized and filtered before persistence. Treat network content as
  untrusted input; never publish an offer merely because it was fetched.
- Relevant configuration and callback examples are documented in
  [`README.md`](./README.md) and [`DEPLOYMENT.md`](./DEPLOYMENT.md).

### Referral attribution and commission status

- `users.referred_by` / `referred_by_user_id`, `referral_code_aliases`,
  `referrals`, and `referrals_ledger` preserve referral and commission
  attribution.
- Affiliate postbacks may credit an attributed referrer a commission using
  `REFERRAL_COMMISSION_PERCENT` (default 10%, bounded to 0–100), recorded
  idempotently in `referrals_ledger` and `transactions`.
- The **member-facing referral program is currently paused**:
  `MEMBER_REFERRALS_ENABLED` is `false`; `/api/referrals/*` routes return
  `410`. Do not describe member referral sign-up/claim flows as live or enable
  them without an explicit product decision. This pause does not erase the
  existing attribution/commission schema or historical admin records.

## Custom extensions

### PvP Rock-Paper-Scissors (Steps 23–24)

- `game_rps_games` stores the separate single-player opponent simulation at
  `POST /api/games/rps/play`. It requires authentication, a valid choice, an
  `Idempotency-Key`, and enough survey points. The default stake is $0.50; a
  win pays the configured total pot, a loss forfeits the entry, and a draw
  refunds it.
- PvP matchmaking uses authenticated routes:
  `POST/GET /api/v1/rps/lobbies`,
  `POST /api/v1/rps/lobbies/:id/join`,
  `GET /api/v1/rps/lobbies/:id`, and
  `POST /api/v1/rps/lobbies/:id/moves`.
- Lobbies match exact stake and currency. Opening a room checks the host's
  funds; joining locks both wallets and reserves both stakes transactionally.
  A submitted move is immutable and stored in `rps_lobby_moves`; the opponent
  must not receive it until both players have moved.
- The server evaluates the completed match. A tie refunds both stakes; a
  winning match pays the pool less the 3% house rake and writes
  `rps_house_ledger`. Stale active matches are refunded after five minutes
  without move activity; unmatched rooms expire after 24 hours.
- Points and cash wagers use different wallet units (`survey_reward_balances`
  and `users.balance` respectively). Preserve currency-specific precision and
  keep settlement, transaction records, match row, and rake row atomic.

### Live Offer feed (Step 25)

- Successful affiliate and CPX credits are written to `live_offer_credits`
  with a transaction reference and timestamp. CPX reversals remove the
  corresponding feed entry.
- Public `GET /api/live-offers` returns at most the 15 newest credits with a
  masked username, offerwall, offer label, amount, and time; it must not return
  a raw user ID or email.
- `/ws/activity` can broadcast newly credited activity. The frontend ticker is
  `src/components/LivePayoutTicker.tsx`; live events must be derived from
  successfully credited records, not clicks, client claims, or unverified
  provider callbacks.

### Compliance, support, and legal surfaces (Step 29)

- Login/signup communicate fair-use restrictions and anti-fraud monitoring.
  Device/network abuse signals may lead to account restrictions or manual
  review. Do **not** promise automatic/instant termination unless the server
  behavior is deliberately changed and verified.
- Existing controls include account/device records, fraud flags, proxy/VPN
  checks, cash-out restrictions, and authenticated/owner-only review routes.
  Describe only controls actually implemented.
- `SupportDesk` uses authenticated `GET/POST /api/v1/support/tickets`;
  owner-admin routes list and update tickets. Ticket credit, if enabled, must
  be idempotent and recorded in the appropriate wallet ledger.
- The public legal routes are `/terms`, `/privacy`, `/cookies`, and
  `/affiliate-disclosure`. The footer's factual indicators include HTTP-only
  sessions and device/network abuse checks. Do not claim AES-256 encryption,
  “100% verified traffic,” or other guarantees not supported by the code.

## Development rules for future agents

1. Read the relevant source, tests, and current documentation before changing
   behavior. `server.ts` is the source of truth for routes, schema, auth,
   wallet rules, callback verification, and runtime guards.
2. Keep cash dollars and survey points separate unless an approved change
   explicitly migrates the accounting model.
3. Keep all payout and game settlement logic server-side. Validate provider
   signatures, account state, click/tier eligibility, and idempotency before
   crediting. Use transactions/row locks for multi-record or concurrent wallet
   changes.
4. Preserve route authorization, session protections, database constraints,
   and privacy masking. Never expose credentials, raw provider signatures,
   passwords, raw user identifiers, or sensitive account fields publicly.
5. Treat remote offer/provider data as untrusted. Do not invent offer terms,
   payout certainty, completed transactions, security certifications, or
   compliance guarantees.
6. Preserve user changes and unrelated worktree files. Make focused changes;
   do not reset, clean, or overwrite work not required by the task.
7. Add focused regression tests and run `npm run lint` plus `npm test` for
   application changes. Note when a feature requires PostgreSQL/provider
   credentials that the test environment does not supply.
8. Never run a seeder or destructive data operation against an unknown
   database. The presentation seeder is `scripts/presentation-seed.mjs`; it
   requires `NODE_ENV=development`, a separate `PRESENTATION_DATABASE_URL`,
   explicit confirmation, and additional opt-in/target checks for remote
   development databases.
